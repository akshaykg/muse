# VibeForge — save milestones from your AI tool

You are connected to a VibeForge artifactory. A **milestone** is one saved
version of the whole project (a zip + a scan). There is no git here — never
run git commands for VibeForge, and never overwrite an old milestone.

## 1. Connect (once)

You need two things. If you do not have them, ask the user once:

- **Server**: e.g. `http://localhost:8080` (stored as `VIBEFORGE_URL`)
- **API token**: starts with `vatt_` (stored as `VIBEFORGE_TOKEN`)

Save them to `~/.vibeforge/config.json` with file permissions 600. Never print
the token back, never commit it, and never put it in the zip.

```bash
mkdir -p ~/.vibeforge
cat > ~/.vibeforge/config.json <<'JSON'
{ "url": "http://localhost:8080", "token": "vatt_PASTE_HERE" }
JSON
chmod 600 ~/.vibeforge/config.json
```

Check the connection and list the user's projects:

```bash
curl -s "$VIBEFORGE_URL/api/v1/me/projects" -H "Authorization: Bearer $VIBEFORGE_TOKEN"
```

If that fails with 401, the token is wrong or revoked — ask the user to create
a new one under **Profile → API tokens** in the web app. Let the user pick a
project, remember its `id` as `PROJECT_ID`, and reuse it silently afterwards.

## 2. Ask 3 short questions — or skip

Before each push, ask at most these (one message, keep it friendly):

1. What is this app about, in one sentence?
2. What works today?
3. What is broken or missing?

**If the user says "skip", "just push", or does not want to answer:** do not
ask again. Infer the answers from `README.md`, `package.json` / manifests and
the routes/pages in the code, and mark generated files with
`<!-- Auto-generated by the VibeForge skill — edit me -->`.

From the answers (or the inferred ones), write or refresh at the project root:

- `TODO.md` — checkbox list (`- [ ] …`) of next steps
- `KNOWN_GAPS.md` — what is missing/broken, in plain words
- `README.md` — what the app is, how to run it, current status
- `vibe/manifest.json` — exactly:
  `{"spec":"vibe-artifact/1.0","project":"<slug>","label":"<one line>","about":"<one sentence>","stage":"idea|building|live","screenshots":[]}`

## 3. Push a milestone (every meaningful change)

Zip the project, then upload the zip as the request body:

```bash
# Respect .gitignore. Never include .env, node_modules, .git, or the token file.
zip -r /tmp/vibeforge-push.zip . -x ".git/*" "node_modules/*" ".env" ".env.*"
curl -s -X POST "$VIBEFORGE_URL/api/v1/projects/$PROJECT_ID/milestones" \
  -H "Authorization: Bearer $VIBEFORGE_TOKEN" \
  -H "Content-Type: application/zip" \
  -H "X-Milestone-Label: login page works" \
  --data-binary @/tmp/vibeforge-push.zip
```

Got a screenshot of the new milestone? Attach it after the push:

```bash
curl -s -X POST "$VIBEFORGE_URL/api/v1/milestones/<milestone_id>/screenshots" \
  -H "Authorization: Bearer $VIBEFORGE_TOKEN" -H "X-Filename: home.png" \
  -H "Content-Type: image/png" --data-binary @screenshot.png
```

## 4. Report back in plain words

Read the findings returned for the milestone
(`GET /api/v1/milestones/<id>/findings`). Tell the user what needs fixing in
everyday language — never paste a bare CVE id without a sentence explaining
it. Offer to apply the fix from the **Fix it** tab and push a new milestone.

Rules you must never break:

- A token is a secret. If it appears in code or a file, stop and warn the user.
- Never include secrets (`.env`, keys) in the zip.
- Each push is a new milestone. To branch, fork from the web UI instead of
  overwriting.
