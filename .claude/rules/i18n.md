# Internationalization Rule

Every user-facing feature must work in any supported language and writing direction. Text, numbers, dates, plurals and layout direction all come from the user's locale. Nothing a user reads is hardcoded in a component.

> **Status:** `@depotex/i18n` exists (`libs/i18n`; how-to in `doc/internal-dev-doc/i18n/`). New and changed UI uses it now. Existing screens are being migrated (phase 2): when you touch a file, move its text into catalogs.

## Locale model

- Locale is a **user preference** stored in Postgres and mirrored in a `locale` cookie, like the theme. The root layout reads the cookie on the server and sets `<html lang={locale} dir={dir}>` before first paint. URLs carry no locale (`/dashboard`, not `/fr/dashboard`).
- First visit with no preference: negotiate from `Accept-Language` against the supported list. The fallback is `en`.
- Fallback chain for a missing message: `fr-CA` → `fr` → `en`, per key. A key missing in a translation falls back to English. A key missing in English is a type error (keys are typed from the English catalogs).
- Supported locales and their direction come from one list in `libs/i18n`. Never hardcode a locale list in an app.

## Text

- **No hardcoded user-facing strings.** This covers visible text and also `aria-label`, `title`, `alt`, `placeholder`, button labels, toasts, validation messages, empty states, confirmation dialogs, `<title>` and metadata.
- Use `t('namespace.key', params)` from `@depotex/i18n`. Keys follow `<namespace>.<area>.<name>` (`repos.create.nameLabel`). The namespace is the feature or package (`setup`, `auth`, `profile`, `repos`).
- **English catalogs are the source of truth**, one JSON file per namespace: `messages/en/<namespace>.json` in the package that owns the feature. Key types are generated from the English files, so a wrong key is a type error.
- **Never build sentences by concatenation** or template literals. Put the whole sentence in the message with named placeholders: `"Deleted {name}"`, not `'Deleted ' + name`. Word order differs by language.
- **Plurals and gender use ICU syntax** in the message (`{count, plural, one {# token} other {# tokens}}`). Never use `count === 1 ? 'token' : 'tokens'`.
- Rich text (links or emphasis inside a sentence) uses tagged placeholders (`"Read the <link>guide</link>"`) rendered by the i18n helper, never split into fragments.
- **Don't translate:** user-entered data, names, IDs, codes, file paths, log output, API field names, units in machine formats. Technical example placeholders (`postgres://…`, `us-east-1`, `0 8 * * *`) stay literal too.
- Don't truncate strings in code (`slice`, `substring`) for display. Use CSS `truncate` / `line-clamp`: languages differ in length and in how characters combine.

## Formatting

- Numbers, currency, percentages, dates, times, relative times, durations, lists and file sizes go through the `@depotex/i18n` formatters (memoized `Intl.*`). Never use hand-built formats (`${d}/${m}/${y}`, `"{m}m {s}s"`, a unit glued to a number in a message), bare `toLocaleString()` without the user's locale, or hardcoded separators.
- Store and send timestamps as UTC ISO strings. Format them only at render time, in the user's time zone preference if set, else the browser's.
- Sort user-visible text with `Intl.Collator` for the current locale, not `<` or `localeCompare()` without a locale.

## Layout and direction

- **Use logical properties only:** `ms-*`/`me-*`, `ps-*`/`pe-*`, `start-*`/`end-*`, `text-start`/`text-end`, `border-s`/`border-e`, `rounded-s`/`rounded-e`. Never `ml-*`, `mr-*`, `pl-*`, `pr-*`, `left-*`, `right-*`, `text-left`, `text-right` for anything that should mirror.
- Technical values (URLs, cron expressions, IDs, keys, IPs, JSON, code) render left-to-right in every locale: `dir="ltr"` (or `<bdi dir="ltr">` inline). The `mono` prop on `Input`/`Textarea` does this for you. Without it, RTL reorders them (`0 2 * * *` shows as `* * * 2 0`).
- Mirror directional icons (arrows, chevrons, back/forward) with `rtl:-scale-x-100`. Icons that aren't directional (search, check, clock) aren't mirrored.
- **Leave room for text expansion.** Translations run 30–40% longer than English, and more for short labels. Buttons, tabs, badges and table headers must wrap or truncate cleanly. No fixed widths sized to English text.
- No text inside images or SVGs. Put it in markup so it can be translated.
- Fonts: each locale's script needs a font. Load extra font subsets (CJK, Arabic, Devanagari) only for locales that need them, through `--dx-font-*` token overrides per `:lang()`, never in every page.

## Performance

- **Translate in Server Components by default.** Text rendered on the server costs no client JavaScript and no catalog download.
- Client components get their strings through the `I18nProvider`, which receives **only the namespaces that route needs** (`<I18nProvider namespaces={['repos', 'common']}>`). Never ship every catalog to the client.
- Catalogs load with dynamic `import()` per locale and namespace, and are cached per process on the server. A locale switch sets the cookie and calls `router.refresh()`, never a full page reload.
- Formatter instances (`Intl.NumberFormat`, `DateTimeFormat`, `PluralRules`, `Collator`) are cached per locale and options. Never create them inside render loops.
- Missing-key and unused-key checks run at build and CI time, not at runtime.

## Backend messages

- **Logs, error messages and audit entries are English only** and never go through translation (see `logging.md`). Only text a person reads in the product is translated, and the frontend does it.

- API errors are translated on the frontend by **`reason`** (the specific cause), then the general **`error` code**, plus `details` parameters, through `apiErrorMessage` with the feature's `reasons` namespace. The backend `message` stays English: it's for logs and API consumers. Every error a user can act on needs a stable reason (see `error-response.md`), never a message matched as a string.
- Text the backend renders itself (emails, alert notifications, exports) uses the recipient's stored locale and Go catalogs with the same keys and fallback chain. Never render it in the server's locale.
- Store keys and parameters, not rendered sentences, for anything shown later in a different locale (audit log descriptions, notifications). Alerts the platform creates set `titleKey`/`messageKey`/`params` (and `labelKey` on actions) next to the English `title`/`message`; the UI renders them with `useAlertText`. Text an admin or plugin writes is user data and isn't translated.

## Plugins

- The plugin host sends `locale` and `dir` in `init` and again in the `theme` message whenever the language changes (optional fields, so protocol v1 stays compatible). The SDK sets `lang`/`dir` on the frame's `<html>` and exposes `dx.locale`, `dx.dir`, `dx.onLocaleChange` and `dx.pickLocale(available)`.
- Plugins ship their own catalogs (a JS module; the sandbox allows no `fetch`) and must follow this rule inside their frame: no hardcoded text, `Intl` formatting in `dx.locale`, logical CSS.

## Testing

- The **pseudo-locale `en-XA`** (accented and about 40% longer, generated from `en`) and **`ar-XB`** (pseudo-RTL) are always available in development. Every new screen is checked in both. Untranslated text and clipped layouts show up immediately.
- Tests assert on keys or roles, not on English copy, unless they test the English catalog itself.
- CI fails on keys missing from `en`, placeholders or tags that differ between locales, invalid ICU syntax, unsupported locale folders, and English keys no code references (`apps/core-frontend/src/__tests__/i18n-catalogs.test.ts`, part of `pnpm test`; `make check-i18n` runs it alone). A new package with catalogs goes in its `CATALOG_DIRS`, and its sources in `SOURCE_DIRS`.
- Keys built at runtime must keep a literal prefix of at least two segments in the code (`` `jobs.types.${type}` ``, `{ reasons: 'tokens.reasons' }`) so the unused-key check can see them.

## Review checklist

- [ ] No hardcoded user-facing strings, including aria-labels, titles, placeholders, toasts and errors
- [ ] No sentence concatenation; plurals use ICU
- [ ] Numbers, dates and lists formatted through `@depotex/i18n`
- [ ] Logical CSS properties only; directional icons mirror in RTL
- [ ] Layout holds in `en-XA` (long) and `ar-XB` (RTL)
- [ ] Client components receive only the namespaces they need
- [ ] User-visible API errors have stable codes and translations
